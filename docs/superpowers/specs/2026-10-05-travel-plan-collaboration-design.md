# RoamBot 同行出行计划设计

日期：2026-10-05
状态：已通过人工评审，等待按阶段实施
范围：在现有推荐、候选对比、账户、收藏与历史能力上新增可选的同行计划协作流程

## 1. 目标

RoamBot 当前能够根据天气、距离、地点热度和多人公平性生成候选，也能够比较 2～3 个候选，但多人场景中的同行者不能直接参与决策。本功能将一次候选对比转化为可保存、可邀请、可投票、可按需复查天气并由发起者最终决策的同行计划。

普通推荐仍可独立完成。用户不登录、不创建计划，也能继续使用现有推荐和候选对比流程。

## 2. 非目标

- 不增加聊天、评论、附件、地图、导航、交通预订或逐日行程。
- 不增加后台定时天气任务、邮件、短信或推送通知。
- 不自动替发起者决定最终地点。
- 不把投票结果混入原推荐综合分。
- 不静默修改原推荐排序、理由或评分。
- 不实现邮箱、手机号、OAuth、密码找回或匿名发起者。
- 不在本阶段创建全新产品首页；该页面作为后续独立设计。
- 不调用真实 Provider 作为自动测试或默认比赛演示的一部分。

## 3. 用户与权限

### 3.1 发起者

- 必须注册或登录现有本地账户后才能创建正式计划。
- 能查看、改名、删除自己的计划。
- 能管理邀请链接、触发天气检查、提交自己的投票、确定最终地点和重新开放投票。
- 能移除错误或重复的匿名参与者；被移除者的投票一并删除。
- 不能修改其他参与者的投票。
- 重新登录同一账户后，可以在任何浏览器从计划中心找回计划。

### 3.2 匿名同行者

- 通过不可猜测的邀请链接进入，无需注册。
- 第一次进入时填写计划内唯一的临时昵称。
- 后端通过通用匿名浏览器身份 Cookie 与计划 ID 找回参与者身份。
- 投票结束前可以修改自己的选择。
- 不能管理链接、检查天气、结束计划、删除计划或修改他人投票。
- 清除 Cookie 或换浏览器后，第一版不提供身份找回；可以使用新昵称加入，发起者可删除重复参与者。

## 4. 核心用户流程

### 4.1 普通推荐

```text
填写条件 → 获取推荐 → 选择候选 → 查看对比 → 结束
```

该流程不要求登录，也不产生正式计划。

### 4.2 同行计划

```text
填写条件
→ 获取推荐
→ 选择 2～3 个候选
→ 查看对比
→ 登录或注册发起者（如尚未登录）
→ 在登录状态下获得可信推荐
→ 创建同行计划
→ 确认名称与预计人数
→ 生成邀请链接
→ 同行者匿名加入并投票
→ 发起者按需检查天气
→ 发起者确定最终地点
→ 出行结束后归档显示
```

## 5. 创建计划的可信来源

只有登录用户能够发起正式计划。计划必须基于该账户在登录状态下产生的推荐历史快照，不能直接相信浏览器回传的评分和天气数据。

规则：

- 登录用户推荐成功时，现有历史捕获流程保存请求与结果，并把对应 `history_id` 随推荐响应返回。
- 前端创建计划时只提交 `history_id` 和选中的 2～3 个候选 ID，不能提交评分、理由或天气内容。
- 后端验证历史属于当前用户、模式为推荐、候选确实存在于该快照，再复制脱敏候选数据。
- 正式计划创建后拥有独立候选快照；之后删除原历史记录不影响计划。
- 游客可以继续独立使用推荐和候选对比，但游客结果不能直接升级为正式计划。
- 游客在已有结果页点击“创建同行计划”时，先登录或注册，再明确提示需要使用原条件重新推荐一次。
- 重新推荐必须由用户确认；Live 模式可能再次调用外部 Provider，不能在登录后静默执行。
- 重新推荐后，如果原候选仍存在可以恢复选择；候选发生变化时要求用户重新选择。

## 6. 计划名称

默认名称由查询城市和日期生成，允许发起者编辑。用户编辑后不自动覆盖。

- 当前年份单日：`苏州 10.10 出行计划`
- 当前年份同月跨日：`苏州 10.10–10.12 出行计划`
- 当前年份跨月：`苏州 10.30–11.02 出行计划`
- 非当前年份：`苏州 27.01.02 出行计划`

紧凑顶部状态省略“出行计划”。确定最终地点后不自动修改计划名称，最终地点作为独立状态展示。

## 7. 数据模型

采用独立同行计划子系统，不改变历史、收藏和公开只读分享的既有语义。

### 7.1 TravelPlan

- ID、发起者用户 ID
- 名称、城市、开始日期、结束日期
- 预计同行人数
- 状态：`voting` 或 `decided`
- 最终候选 ID、决定时间
- 创建时间、更新时间

预计人数默认取本次查询中的出发地数量，发起者可以调整。预计人数只用于进度提示，不作为参与硬上限。实际参与人数超过预计人数时只显示“6 人已参与”，不显示 `6/5`。

### 7.2 PlanCandidate

- 计划 ID、候选顺序
- 地点公开信息
- 创建计划时的原推荐分数、理由与排序快照
- 距离聚合与多人公平性
- 创建计划时的天气快照

原推荐快照创建后不可覆盖。

### 7.3 PlanParticipant

- 计划 ID
- 昵称及其规范化值
- 发起者用户身份或匿名浏览器身份哈希，两者取其一
- 角色、加入时间

数据库约束计划内规范化昵称唯一。发起者也作为参与者提交自己的选择。

### 7.4 PlanVote

- 参与者 ID
- 一个首选候选 ID
- 更新时间
- 若干可接受候选关联

首选自动计入可接受人数，前端无需重复勾选。

### 7.5 PlanInvite

- 计划 ID
- 邀请令牌哈希
- 创建时间、过期时间、撤销时间

链接默认在出行结束日期后 7 天过期。换新链接后旧链接立即失效。

### 7.6 PlanWeatherCheck

- 计划和候选 ID
- 触发者用户 ID
- 检查时间、数据来源、成功或失败状态
- 最新天气快照
- 风险等级与相对上次的变化摘要

删除计划时级联删除候选、成员、投票、邀请和天气检查。第一版不提供回收站或恢复。

## 8. 状态与生命周期

```text
投票中 ──发起者确定地点──> 已决定
已决定 ──发起者重新开放──> 投票中
任意状态 ──发起者删除──> 永久删除
```

重新开放投票时保留成员与投票，清除最终候选和决定时间，不自动换新邀请链接。

已决定计划的顶部状态保留至出行结束日期。出行结束后顶部入口隐藏，计划进入计划中心的“已结束”区域。正式计划持续保存，直到发起者永久删除。

## 9. 邀请与投票

### 9.1 邀请

- 邀请令牌不可猜测，数据库只保存哈希。
- 发起者可以复制、撤销和换新链接。
- 邀请链接有效时，计划决定后转为只读。
- 链接到期、撤销或计划删除后不再返回计划内容。

### 9.2 投票

- 每位参与者必须选择一个首选。
- 可以额外选择多个可接受项。
- 未提交自己的投票前，匿名同行者不能查看他人选择或汇总。
- 提交后可以查看当前汇总并在投票结束前修改。
- 发起者始终可以查看完整汇总，但不能替其他人投票。
- 决定后所有有效邀请访问者都能查看最终汇总和最终地点，不能继续投票。

每个候选展示首选票数、可接受人数、已投票人数、是否所有已投票成员都能接受、原推荐综合分、原公平性和最新天气风险。未达到预计人数时必须标为“当前结果”，不能写成最终共识。并列票数如实展示，最终决定始终由发起者完成。

## 10. 隐私与安全

- 邀请页只显示城市、日期、候选公开信息、平均路程、最大路程和多人公平性。
- 不显示原始出发地、坐标、路线或昵称与出发地的对应关系。
- 发起者详情与公开邀请页使用不同响应模型；公开响应采用字段白名单。
- 匿名浏览器身份使用通用 `HttpOnly`、`SameSite=Lax` Cookie，数据库只保存哈希。
- 匿名投票写操作还需匿名会话 CSRF 值。
- 发起者写操作使用现有登录会话和 CSRF。
- 无权访问他人计划统一返回 404，避免泄露资源存在性。
- API、日志、测试和文档不得输出完整邀请令牌、Cookie、Provider 密钥或其他秘密值。

## 11. API 设计

### 11.1 发起者

```text
GET    /api/v1/plans
POST   /api/v1/plans
GET    /api/v1/plans/{plan_id}
PATCH  /api/v1/plans/{plan_id}
DELETE /api/v1/plans/{plan_id}
DELETE /api/v1/plans/{plan_id}/participants/{participant_id}

POST   /api/v1/plans/{plan_id}/invite/rotate
DELETE /api/v1/plans/{plan_id}/invite

PUT    /api/v1/plans/{plan_id}/vote
POST   /api/v1/plans/{plan_id}/weather-checks
PUT    /api/v1/plans/{plan_id}/decision
DELETE /api/v1/plans/{plan_id}/decision
```

### 11.2 匿名同行者

```text
GET  /api/v1/public/plans/{invite_token}
POST /api/v1/public/plans/{invite_token}/join
PUT  /api/v1/public/plans/{invite_token}/vote
```

### 11.3 稳定错误码

- `plan_not_found`
- `history_not_eligible`
- `candidate_not_in_history`
- `nickname_taken`
- `invite_expired`
- `invite_revoked`
- `vote_closed`
- `participant_required`
- `weather_check_cooldown`
- `provider_unavailable`
- `invalid_plan_transition`

前端不得依赖英文错误文案判断分支。

## 12. 天气检查

- 只有发起者可以触发。
- 投票中检查全部 2～3 个候选；已决定后只检查最终地点。
- 出行日期结束后不再允许检查。
- 使用现有天气缓存策略，一小时内不强制绕过缓存；界面显示下次可检查时间。
- 原推荐快照保持不变，天气检查作为独立动态信息。
- Provider 失败时保留上次有效结果，记录本次失败，不自动重试。
- 风险变化由确定性规则计算，不使用 LLM。

变化等级：

- 稳定
- 需留意
- 明显恶化
- 天气条件改善

## 13. 前端结构

### 13.1 当前导航调整

删除独立“首页”按钮，保留“推荐”作为当前默认工作区入口。当前阶段 `/` 仍是推荐工作区。

桌面右侧导航：

```text
[计划中心] [推荐] [收藏] [历史] [账户]
```

RoamBot 品牌与“推荐”均回到推荐工作区并恢复初始推荐状态。

未来全新产品首页是独立阶段：届时 `/` 改为产品首页，当前工作区迁移到 `/recommend`，品牌进入首页，“推荐”进入 `/recommend`。本阶段不创建占位首页。

### 13.2 创建计划

候选对比结果下增加次级操作“创建同行计划”。创建确认只包含默认名称、预计同行人数、已选候选摘要和创建操作。只有当前推荐响应包含属于该登录账户的 `history_id` 时才能创建。游客先登录或注册，再经明确确认使用原条件重新推荐；不能静默调用 Provider。

### 13.3 计划中心

`/plans` 需要登录，分为“进行中”和“已结束”。列表显示名称、日期、状态、参与进度、当前共识或最终地点、最近天气检查时间。未完成登录和正式创建的游客结果不出现在计划中心。

### 13.4 发起者详情

`/plans/{plan_id}` 展示计划信息、邀请管理、参与进度、投票汇总、候选快照、最新天气、参与者管理、发起者投票和最终决策操作。

### 13.5 同行者邀请页

`/join/{invite_token}` 支持临时昵称加入、首选与可接受项投票、提交后查看汇总、修改投票和决定后的只读结果。

## 14. 顶部动态计划状态

“计划中心”位于右侧导航块最左侧，同时作为动态状态的锚点。

桌面：

- 无活跃计划时是普通导航按钮。
- 创建新计划后，以右侧为固定点向左弹性展开，右侧其他导航不移动。
- 完整状态展示数秒后收成较短胶囊。
- hover 或键盘聚焦时再次展开。
- 点击进入计划中心并默认打开当前计划。
- 同时存在多个活跃计划时，显示距离出行日期最近的一项。
- 动画借鉴形状变形和弹性减速原则，但使用 RoamBot 自身颜色、圆角、边框和阴影，不复制其他产品视觉。

移动端：

- 第一行使用 `[RoamBot] [紧凑计划状态] [账户]`。
- 第二行使用 `[计划] [推荐] [收藏] [历史]`。
- 新计划创建后状态短暂展开，随后收进紧凑状态。
- 无活跃计划时第一行中间保持空白。
- 不进行桌面宽度的横向展开。

所有动画支持 `prefers-reduced-motion`；减少动态效果时直接切换状态。出行结束后状态收回并隐藏。

## 15. 响应式与可访问性

- 手机计划列表、详情和邀请页采用单列卡片，不复制桌面宽表格。
- 首选使用单选控件，可接受项使用复选控件，整行可点击。
- 触摸目标约 44 px 或更大。
- 核心操作可通过键盘完成，动态状态有可访问名称。
- 状态变化使用克制的 `aria-live`，不播报每一帧动画。
- 桌面与 390×844 手机视口均不得产生整页横向溢出。
- 移动端优先使用系统分享能力，不支持时复制邀请链接。

## 16. Mock 与 Live 边界

- Mock 模式完整使用真实 FastAPI、SQLite、账户、邀请、投票和计划流程。
- 天气检查调用 Mock Provider，默认重复检查显示“无明显变化”，不使用随机数伪造风险变化。
- 后端测试通过受控 fixture 覆盖风险上升、恶化、改善和失败。
- 不新增只为比赛演示服务的隐藏后门接口。
- 演示材料明确标记地点与天气来自 Mock。
- Live Provider 验证需另行授权并如实记录；Mock 通过不能写成 Live 已验证。

## 17. 验证范围

后端测试必须覆盖数据约束、级联删除、所有权、邀请换新与到期、匿名身份、昵称唯一、投票可见性、投票修改、状态转换、天气权限和冷却、失败保留，以及公开响应不泄露地址和坐标。

前端测试必须覆盖创建确认、计划中心、发起者详情、匿名加入、投票、结果可见性、错误状态、动态导航、移动端布局和减少动态效果。

桌面与手机 E2E 至少覆盖：

```text
游客推荐
→ 选择 2～3 个候选
→ 注册或登录
→ 创建计划
→ 复制邀请链接
→ 匿名同行者加入并投票
→ 发起者查看汇总
→ 检查天气
→ 确定最终地点
→ 顶部状态改变
→ 邀请页转为只读
```

## 18. 分阶段实施

### 阶段 0：当前 UI 基线

删除误加的“三步快速开始”，删除独立首页按钮，保留推荐入口；保持滚动对齐、候选对比引导和 hover。全量门禁与人工验证通过后再形成基线。

### 阶段 1：计划模型与发起者 API

让登录推荐响应返回所属历史 ID；实现迁移、仓储、服务、从可信历史创建计划、列表、详情、改名、删除和发起者参与身份。

### 阶段 2：邀请、匿名身份与投票 API

实现邀请生命周期、匿名 Cookie、临时昵称、投票修改、先投后看和公开字段白名单。

### 阶段 3：天气与状态转换

实现天气快照、冷却、风险变化、失败保留、最终决定和重新开放。

### 阶段 4：创建流程与计划中心前端

实现登录后可信推荐、游客登录后明确重新推荐、创建确认、计划中心和发起者详情。先使用普通计划导航，不加入复杂动画。

### 阶段 5：同行者邀请页

实现匿名加入、投票、汇总、修改和决定后只读，覆盖手机单列流程。

### 阶段 6：顶部动态状态

在业务稳定后实现桌面向左展开、紧凑胶囊、移动端状态、出行结束隐藏和 reduced-motion。

### 阶段 7：端到端验收与参赛材料

运行后端、前端、构建和桌面/手机 E2E；完成架构图、截图、视频脚本、风险边界和 AI Coding 证据。

## 19. 湛卢执行方式

- 先发送一次总交接 Prompt，说明完整设计、仓库状态与禁止事项。
- 每个阶段单独发送一次执行 Prompt，不允许自动进入下一阶段。
- 当前阶段内预先授权读取相关代码、修改列明文件、运行 Mock 聚焦测试与静态检查，无需为每个普通操作重复请求许可。
- 每阶段必须先产生因目标行为缺失而失败的有效 RED，再做最小 GREEN。
- 阶段结束时展示 diff、实际测试命令与结果、未验证边界和过程证据，然后等待人工批准。
- 依赖下载、Live Provider、破坏性迁移、扩大范围、Commit、push、PR 和 merge 仍需单独授权。
- 不设置 Token 预算；阶段拆分用于保证正确性、审查质量与比赛证据，而不是节省 Token。

## 20. 比赛证据

每阶段保留：需求拆解、代码理解、方案比较、有效 RED、GREEN、失败与修正、人工审查、被拒绝建议、关键 diff、测试输出和 Commit 对照。不得补造历史过程，也不得把暑期训练营已有代码写成湛卢生成。

最终材料必须明确区分：Mock 验证、Live 验证、自动测试、人工浏览器检查和仅有代码但尚未验证的内容。
