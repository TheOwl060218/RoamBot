# RoamBot 核心编排重构设计

日期：2026-10-16。状态：设计待用户审阅，尚未实施本次重构。

## 1. 已确定的方向与范围

用户选择：重构最影响体验的核心编排，保留可复用的业务系统，暂不整体换框架。
目标是减少推荐等待、重复理解和搜索消耗，同时保持自然语言理解、事实依据及实际业务执行正确。
本设计只重构推荐执行与业务分流的衔接，不重写整个网站或扩大产品范围。

- 保留现有业务工具、执行日志、身份、CSRF、权限、幂等、收藏、计划、邀请、投票和分享服务。
- 保留已有地图、天气、公开搜索适配器和缓存；沿用当前模型，不引入 LangGraph、MCP 或新收费服务。
- 保留开放休闲需求、按需日期和出发地、单行多体验穿插、整卡详情、独立按钮和层级浮层。
- 工作目录为 `.worktrees/assistant-business-tools`，分支为 `feat/conversational-business-tools`。
  保护既有未提交修改，尤其是尚未完成最终验收的历史/分享/计划接入；不自动提交或部署，不动8026。

## 2. 现状与可验证的瓶颈

`DiscoveryWorkflow.run()` 当前执行：一次规划 → 检索 → 首批事实 → 首批生成及审查 →
后续提名 → 后批逐批事实、生成及审查 → 必要时补查。每次 `compose()` 通过
`DiscoveryRun.act('publish_batch')` 再进入语义审查。检索和事实请求已有局部并行。

这些是小样本，部分质量未达到要求，不是平均值、P95或正式可用证明。

并行之后各阶段累计时间可能重叠，必须另记关键路径，不能用累计时间占比冒充墙钟时间占比。

当前复用边界不足：规划、提名、事实收集、生成、审查均可修改运行对象中的地点、证据、
覆盖状态或指标。不能直接将这些现有方法放到线程池中并发运行。

## 3. 方案比较与选择

| 方案 | 适用收益 | 限制 |
| --- | --- | --- |
| 仅调整批大小、提示词和缓存 | 可快速改善局部耗时 | 串行等待和共享状态耦合仍存在 |
| 分离计算与提交，重构有限并行编排 | 直接缩短关键路径，保留实际业务与可回退基线 | 需要验证取消、版本、覆盖和发布一致性 |
| 整体迁移通用Agent框架或重写业务 | 可获得额外状态管理能力 | 迁移并不自动减少模型调用，当前没有证据证明投入更划算 |

选择第二项。先做可对比的新编排器，不恢复自由循环式Agent，也不为不同路径额外增加分类模型。
长期任务跨进程恢复不是本轮交付承诺；现有历史恢复接口继续保留。

## 4. 执行结构

沿用一次结构化规划产生本轮意图、修改操作、必要体验、自由检索方向及可用业务方案。
业务意图进入既有执行器；搜索意图进入新的推荐协调器。
上下文不足、权限不足或对象歧义沿用相应业务处理，不绕过已有确认。

推荐协调器执行：

1. 冻结本轮输入、已核实上下文及任务版本。
2. 按方向取得公共资料和地图候选；只对缺口发起预算内的公开搜索。
3. 选择少量、覆盖不同实际体验的首批候选，取得本轮必需的路线/天气及地点证据。
4. 首批生成进入审查时，并行准备后批的事实和生成。
5. 审查完成后由唯一协调器提交卡片；按固定批次顺序追加。
6. 根据已审查的全局覆盖决定是否需要补查，合并补查请求并受预算约束。
7. 等待已启动任务结束或进入取消终态后，保存最终实际快照。

普通搜索不调用完整业务规划器。常见操作继续复用同次理解；复杂业务保留原有回退路径。
本轮不通过增加一轮“快慢分类”模型来实现分流。

## 5. 模块与内部合同

### 输入与结果

新增内部执行合同，包含 `run_id`、身份作用域、任务版本、批次序号及输入指纹。
输入指纹覆盖用户需求、当前上下文、地点ID、证据内容及版本、相关路线/天气和规则版本。
地点ID、短时序号及证据ID仍由服务端真实对象绑定，模型不能指定身份或任意执行URL。

后台任务只接收深拷贝或不可变输入，返回事实结果、生成草稿或审查结果。
后台任务不能直接修改 `places`、`evidence`、`cards`、`covered_directions`、历史或业务数据库。
任务调用统计使用线程安全计数；工作任务失败不导致另一任务的统计丢失。

### 协调器

新协调器管理依赖、批次序号、取消、任务版本、搜索预算、并发许可和最终状态。
保持现有job的创建、轮询、取消、恢复接口及前端快照结构。
`metrics` 可增量扩展；不要求前端理解内部任务图。

### 共享提交出口

从现有发布流程提取服务端内部提交出口，供旧路径和新协调器复用。
旧工具路径仍先完成审查；新路径传入与完整输入指纹绑定的审查结果，避免提交时重复调用审查。
该结果不能来自客户端或模型自行声明的“已通过”。提交时重新核对任务版本、证据归属、
硬约束、去重和取消状态；通过之后才修改快照。

审查结果使用本批冻结的需求和证据。全局体验覆盖由协调器根据提交成功的审查结果合并。
不得让并行批次读取并修改同一个 `evidence_query`；补查线索统一交给协调器去重处理。

### 文件边界

- 新增 `domain/discovery_execution.py`：内部任务输入/输出和版本合同。
- 新增 `services/discovery_orchestrator.py`：有限并行、单一提交、补查及预算。
- `services/discovery_workflow.py`：保留可对比基线，提取可复用的准备与校验逻辑。
- `services/discovery.py`：提取内部提交出口，维护既有job/快照生命周期。
- `providers/discovery_workflow.py`、`providers/discovery.py`：保留模型和地图协议，增加紧凑输入及用量记录。
- `persistence/discovery_cache.py`：需要时复用已有单航次合并能力，不缓存私有资料到公共库。
- `api/routes/discovery.py`：工厂选择新旧实现，保留外部API、身份及归档回调。
- 测试和验收文档：加入调度、取消、预算、准确性与真实对比记录。

不借本轮重构修改其他业务语义。历史/计划新格式的既有待验收改动单独列入回归范围，
不把其通过归因于编排提速，也不在本轮重写。

## 6. 有限并行与发布顺序

- 每个推荐job最多同时运行两次模型请求，进程共享最多两次发现流程模型请求许可。
  获取许可必须可取消、有截止时间；计时区分排队和请求，避免把排队误判成模型生成。
- 独立地图/天气读取可继续使用现有最多四工作线程和地图限速；不通过放开高德限速提速。
- 模型并行任务中不再嵌套提交并等待同一模型线程池，避免资源耗尽后互相等待。
- 首批序号0优先取得模型许可。首批进入审查后，后批才可以占用另一模型许可，避免抢占首屏资源。
- 不预先生成大量最终不会展示的卡片。候选总量沿用本轮最多12个，每次发布最多6个。
  首批优先2–3个有依据的不同体验；只有一个可靠候选时允许发布一个，不等凑齐数量。
- 后批可以先计算完，但必须等更早批次通过、明确失败或超时后再追加。
  已发布卡片不重排、不替换。全局覆盖只统计实际提交的卡片。
- 存在硬距离上限时，路线未核实或超限的候选不能发布；前几个被淘汰后继续检查后续候选。
  没有日期不查天气，没有中心不编路线；不回到六类必选表单。
- 不为了并行而新增模型调用。短提示、减少重复资料和确定性去重才可能减少token。

## 7. 减少调用与用量的规则

先减重复输入和不必要阶段，再评估是否能复用审查；不能以换框架或加缓存名称代替实际提速。

- 保留真实需求原文、改口、否定、角色与必要上下文，只裁剪重复元数据及无关资料段落。
  证据仍能追溯到真实地点和原来源，不得通过过度摘要丢掉限制条件。
- 公共证据已足够时跳过重复提名；缺口才补查，不按热门地点数量判断全需求已经满足。
- 各卡片理由保持具体，不重复输出整份地点资料；独立审查保留重要语义和时效判断。
- 第一版不引入相似语义命中缓存，不允许用“同一城市/同一类型”复用个性化结果。
  精确缓存仅在完整生成输入或完整审查输入的指纹相同、身份作用域和有效期均满足时适用。
  对话、否定、日期、路线、天气、证据、理由或规则变动都会失效；失败和未通过结果不作为通过缓存。
  公共库只保存原有地图/网页事实，生成及审查缓存仍为短时私有缓存。
- 冷请求默认先一次公开搜索，整轮最多两次实际搜索，重试也占预算；并发用原子预留，
  不能两个任务各看到剩余1次而同时超支。
- 保留现有整轮最多10次模型请求和120秒边界；格式修复、失败请求也计次数。
  后台工作继承同一截止时间，超时后不得再提交或触发写操作。

精确缓存的收益是待测假设；不据此保证所有查询更快，也不把减少审查当成默认优化。

## 8. 取消、变更与副作用

用户取消、改口或切换账号后，旧任务即使收到模型响应也不能提交到当前结果。
已发出的同步HTTP请求不声称能够物理撤销；到达后丢弃陈旧响应并记录已发生的用量。
进程许可只在真实请求退出后释放，不能取消时提前释放造成实际超并发。

地图/天气/公开资料为读取，不在这些工作任务中创建收藏、计划或分享。
业务写入只通过原执行器，继承身份、对象绑定、版本及幂等。
归档回调只处理最终实际快照；部分结果、错误和缺口状态保留，不将“有卡片”写成“需求全完成”。
新旧实现只在隔离验收中分开运行，不向同一个用户页面同时发布两套卡片，
不对写操作做双执行。回退使用已有配置/工厂边界，不清除用户数据。

## 9. 测量与验收

### 必记指标

记录首批可交互时间、整轮墙钟时间、任务依赖及开始/结束时间、模型次数、
许可排队时间、模型请求时间、检索/地图/天气时间、缓存命中、各批提交时间及实际卡片。
记录接口返回的输入/输出token和Tavily usage；缺失记为未知，不记为0。
不声称总HTTP耗时已经拆出了纯网络或纯推理时间。诊断报告不包含凭据、Cookie或原始私有位置。

### 自动验收

先建立旧实现可重放基线与可控延迟的Mock测试，不调用真实Provider：

1. 后批准备与首批审查确实重叠，首批不被后批占满许可。
2. 乱序响应仍按批次追加，不重复、不改变已发布卡片位置。
3. 多用户及同用户多job不串用地点、证据、任务版本或私有缓存。
4. 取消、超时、改口和切换身份后，无陈旧发布、归档或业务写入。
5. 模型、搜索预算在并发、失败及格式修复下仍受限；无许可泄漏或嵌套死锁。
6. 排除条件、实际路程上限、日期按需、跨地点引用、旧资料与体验覆盖回归不弱化。
7. 当前选项被硬约束淘汰后，仍检查后续可行候选；多样性不能靠标签改名伪装。
8. 缓存的理由、证据或需求变化会失效；未知usage、失败请求计数正确。
9. 原业务分流、确认、权限、收藏幂等及历史/分享/计划接口不回归。
10. 桌面与手机Mock浏览器验证首批可点击、追加时卡片和详情保持、嵌套地图返回、
    键盘操作、快速连续消息及reduced-motion。

### 限定真实比较

先重放保存的资料和反例，验证结构及调度；重放不能证明真实模型准确率。
之后沿用已有真实调用授权，在隔离业务数据中做首轮最多4次推荐运行：
已有公共资料和新地区各选一个请求，新旧实现各一次；首轮Tavily实际credits上限4。
usage不明确时暂停继续付费请求并报告，不把未知值当免费。对比记录串行执行，
避免新旧测试相互抢占模型资源；各自使用相同的初始缓存快照，不能让后运行者免费继承前者结果。
另外复用原有业务样例检查操作分流，不能把“查找”意图错误跳过成业务完成。

首轮采用小样本，不报告P95或全场景准确率。原始草地、同名、父子地点、过期资料等
失败样例继续保留；不能换成容易通过的表达或删除失败断言。

### 替换条件

新编排默认启用前，自动并发及业务回归必须通过；真实比较必须同时报告时间、
实际结果和用量。已有资料样本期望首批和总时间均比同条件基线缩短至少20%，
这是验收目标而非承诺；冷请求不得新增错误或突破搜索预算。
小样本改善只允许标为阶段改善。若速度目标未达或出现新的语义错误，保留旧默认，
解释瓶颈及失败，不自动降低标准、不直接部署。

## 10. 顺序与本阶段交付

设计审阅 → 详细实施计划 → 先补计时/可重放基线 → 分离计算与提交 → 有限并行 →
紧凑输入及精确复用 → 自动回归 → 限定真实对比 → 更新交接与本地运行版本。
按阶段批量验证，不每个小改动跑全量，也不先在8033替换尚未验收的编排。
最终交付记录明确区分已修改、Mock通过、浏览器通过、真实模型通过及残余问题。

## 11. 参考与采用范围

- [Anthropic：Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)：
  简单可组合流程、并行独立任务、用可测收益决定复杂度；不照搬模型或改成无限工具循环。
- [LangGraph overview](https://docs.langchain.com/oss/python/langgraph/overview)：
  状态和执行管理可作为以后需求明确时的候选，本轮不迁移框架。
- [渐进替换模式](https://martinfowler.com/bliki/StranglerFigApplication.html)：
  替换核心子系统并保留既有业务，采用隔离对比及可回退的切换。

上述资料支持设计模式，不能证明RoamBot实际性能。本项目收益以本节验收记录为准。
