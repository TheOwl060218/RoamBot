# RoamBot 真实推荐质量改进设计

## 1. 目标与范围

本次解决真实 Provider 接入后暴露的四类功能问题：候选类型被单一类别垄断、天气对不同场景的影响缺少区分、原“景区人气”依据不可靠、推荐理由在 LLM 降级时没有实际意义。

本次不加入地图、导航、行程安排、实时客流、立即出发或小时级出发时间。整体双栏排版、颜色语义和多日卡片布局另行统一设计；功能实现只做展示新数据所需的最小前端调整。

本设计取代既有设计中与“景区人气/景区热度”、固定五个结果、逐地点标签覆盖惩罚、统一天气惩罚和单批次推荐理由生成有关的条款；既有登录、收藏、历史、分享、凭据保护和 Provider 降级边界保持不变。

## 2. 候选数量与类型覆盖

### 2.1 结果数量

- “匹配任意一种”默认目标为 5 个结果。
- “尽量覆盖全部”的目标数量为已选类型数加 1，同时不得少于 5、不得多于 7。
- 因候选不足、超出最大距离、数据无效或必要天气数据不可用，实际结果可以少于目标数量；系统不得为凑数返回不相关地点。

### 2.2 覆盖语义

“尽量覆盖全部”改为列表级语义：当有效候选存在时，最终列表整体至少覆盖一次每个已选风景类型，而不是只对单个地点计算标签覆盖比例。

候选选择分为两阶段：

1. 高德仍按每个已选类型执行一次 POI 搜索，合并后按 POI ID 去重。
2. “尽量覆盖全部”先以贪心方式选择能覆盖尚未覆盖类型的候选，再用其余候选补足目标数量；“匹配任意一种”直接选择综合条件较好的候选。

昂贵的精确距离与天气调用只作用于最多 7 个预选候选。预选使用已选类型覆盖数、高德地点评分、粗略直线距离和类型内检索顺序；不得再使用类型拼接后的全局序号制造跨类型优势。

天气不佳不会使有效候选自动退出覆盖列表。超出用户最大距离仍是硬约束。某个类型确实无法覆盖时，响应提供结构化原因，前端统一提示。

## 3. 地点评分

原“景区人气/景区热度”改为“地点评分”。高德 POI 请求增加 `show_fields=business`，从同一次响应读取景点可用的 `rating`，不增加 POI 请求次数。

- API 保存高德原始五分制评分或 `null`。
- 前端显示 `4.7 / 5`；缺失时显示“暂无数据”。
- 评分参与内部排序时换算到统一尺度，但前端不展示换算分。
- 评分缺失不视为差评：计算该候选指数时移除评分分项，并将它原有的显示权重按其余可用分项当前权重的比例重新归一化；多人公平性固定 20% 不参与这次重分配。
- 高德类型内检索顺序只作为候选预选和最终同分规则，不再作为面向用户的人气指标。
- 单人默认显示权重改为天气 40%、距离 30%、地点评分 30%；多人仍把三项显示权重乘以 80%，公平性固定占 20%。

结果区统一说明：

> 地点评分数据来源：高德开放平台；出游匹配指数仅用于比较本次候选地点，不代表官方评价。

## 4. 场景暴露类型

天气判断根据地点标签派生三类场景：

- 室内型：只有博物馆等室内标签。
- 户外型：只有湖景、海景、古镇/历史街区、公园/绿地/湿地、山地/徒步等户外标签。
- 混合型：同时包含室内与户外标签。

缺少有效标签时按混合型保守处理，并在内部来源信息中标记分类有限；不向用户展示技术错误。

## 5. 天气适配与逐日出行建议

内部天气分继续用于排序，但前端不显示分数、扣分值或 `极端温度 -40` 之类实现细节。相同天气按场景使用不同影响强度：户外最大、混合居中、室内最小；低能见度等整体出行因素仍影响三类地点。

沿用现有降水、温度、风速、能见度和紫外线边界，并调整影响矩阵：

| 因素档位 | 户外型 | 混合型 | 室内型 |
| --- | ---: | ---: | ---: |
| 微量/一般/强降水 | 10 / 35 / 60 | 8 / 25 / 45 | 5 / 15 / 35 |
| 轻微/明显/极端温度 | 10 / 25 / 40 | 8 / 18 / 30 | 5 / 10 / 15 |
| 较强/强/大风 | 10 / 25 / 40 | 5 / 18 / 30 | 0 / 10 / 20 |
| 紫外线强 | 10 | 5 | 0 |

能见度继续按现有规则影响全部类型。表中数值只用于内部计算，不进入前端文案。

逐日状态根据调整后的内部适配值产生：

- `>= 75`：适合前往。
- `>= 50 且 < 75`：谨慎考虑。
- `< 50`：不建议当日前往。

自然语言原因必须包含日期、实际天气值、场景差异和可执行建议。例如：

> 7月25日最高温度预计达到36℃，湖景属于户外场景，建议避开高温时段并做好防暑准备。

多日总体状态：全部适合为“适合前往”；至少一天谨慎且没有不建议为“部分日期需谨慎”；至少一天不建议为“部分日期不建议前往”。总体状态不替代逐日状态。

出游匹配指数和出行建议状态是独立概念。指数负责候选比较；状态负责说明具体日期是否适合出行。颜色只作为未来辅助表达，文字状态始终存在。

## 6. 推荐理由

后端必须先生成完整、可用的本地事实理由，再允许 LLM 润色。事实至少包含：

- 命中的已选风景类型；
- 是否为满足“尽量覆盖全部”而保留；
- 距离和预计时间；
- 逐日出行建议状态及主要天气原因；
- 高德地点评分或评分缺失；
- 主要优势、限制和排序取舍。

LLM 接收这些事实，以及用户选择的类型、覆盖模式和显示权重。LLM 只能改善中文表达，不得修改候选、事实、指数、排序或状态。

LLM 提示只使用概括后的距离和预计时间，不包含用户输入的精确出发地、同行人标识或其他个人信息。

- 每个 LLM 请求最多处理 2 个地点。
- 1～2 个结果最多 1 次，3～4 个最多 2 次，5～6 个最多 3 次，7 个最多 4 次。
- 某组失败或格式无效时不自动重试；该组使用本地事实理由，其他成功组保持 LLM 结果。
- 本地理由必须是自然中文，不得出现英文模板、内部字段名、原始权重或内部扣分。

面向用户的标题继续使用“推荐理由”。

## 7. Provider 调用与缓存边界

单次推荐上限调整为：

- 高德地理编码：3 次。
- 高德 POI 搜索：6 次。
- 高德距离：7 次。
- QWeather 天气：7 次。
- LLM：4 次。

高德评分来自现有 POI 搜索响应，不增加请求。所有调用继续顺序受预算控制，不自动重试。缓存 TTL 和失败降级边界保持不变；自动测试与 CI 仍强制 Mock/demo 模式并禁止真实网络调用。

## 8. 数据与兼容性

- 地点模型新增可空的高德五分制评分。
- 推荐结果新增总体出行建议和逐日出行建议状态，保留原始天气事实和内部数值供排序使用。
- Mock 和苏州内置演示地点补充确定性的评分或评分缺失样本，用于离线测试完整状态，而不伪装成高德实时数据。
- 历史、收藏详情和公开分享采用同一展示数据；旧历史快照缺少新字段时按“评分暂无数据”和现有天气重新派生展示状态，不删除用户数据。
- 分享快照继续使用深层白名单，不包含精确个人起点、凭据、Cookie 或 LLM 提示原文。

## 9. 最小前端改动与后续视觉清单

本轮功能实现允许的最小前端改动：

- “景区热度/景区人气”改为“地点评分”，显示原始 `X.X / 5` 或“暂无数据”。
- 显示总体和逐日出行建议文字状态。
- 日期显示为“7月25日”。
- 隐藏内部天气扣分；显示自然语言天气提醒。
- 结果区统一显示评分来源和指数说明，不在每张卡重复。

以下视觉问题保存到后续统一前端设计，不在本轮零散修改：

- 左侧筛选区停留在顶部、右侧结果过长造成的双栏失衡。
- 推荐卡整体信息密度与纵向长度。
- 两日至七日天气卡片的稳定时间序列布局；五日不得出现不规整的 `4 + 1` 孤立换行。
- 日期、天气、状态、温度和原因的字体层级。
- 指数与状态的并列位置。
- 状态颜色的语义选择；不得仅依赖红绿表达。

## 10. 验证

- 候选测试覆盖任意模式、列表级全覆盖、1～6 个已选类型、最多 7 个结果、去重、候选不足和类型无法覆盖提示。
- 高德适配器测试覆盖 `show_fields=business`、合法/缺失/畸形评分，证明无额外详情请求。
- 排序测试覆盖评分可用、评分缺失时权重重分配和跨类型顺序不偏置。
- 天气测试覆盖室内、户外、混合型在各阈值边界的内部适配值、逐日状态和多日总体状态。
- 理由测试覆盖事实保底、两地点分组、最多四次调用、部分组失败不重试、严格事实校验和隐私字段不进入提示。
- API、历史和分享测试覆盖新字段与旧快照兼容。
- 前端组件测试覆盖地点评分、来源说明、中文日期、逐日状态和无内部扣分文案。
- Playwright 使用 Mock provider 验证推荐、历史、分享在桌面和移动端可用；真实 API 只在用户逐次批准的人工测试中调用。
