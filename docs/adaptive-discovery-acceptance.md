# 按需检索、公共证据与业务引用 · 2026-10-16

本阶段目标是同时改善速度、准确性与搜索消耗，持续目标仍未完成。

## 已修改

- 先查公共证据索引，再决定是否联网。已有足够地图实体与出处时省去重复的地点提名模型调用。
- 冷请求先一次基础搜索；仅缺核心依据或缺少不同体验时补查，每轮实际搜索尝试最多两次。
  命中私有短时缓存不计新搜索，失败尝试仍计预算，缺少完整usage时费用记为未知。
- 共享的是实际地图地点和关联公开网页，不是原句、用户偏好、私有位置或模型编造的事实。
  使用SQLite FTS5与Unicode字符gram检索，不引入六类字典、外部嵌入模型或新收费服务。
- 公开索引按场所截取文章章节，避免合集里另一家场所的设施被算到当前地点；只用正向活动词
  检索，地区单独过滤。实际路线仍由真实路线服务核实，索引的空间粗筛不能替代实际路程。
- 缓存重复读取不刷新原地点核实时间和网页取得时间，过期资料不能因反复使用而永久变新。
- 理由引用短片段ID，程序核实片段实际存在且属于该地点；明确活动要求需要逐项证据。
  地图地址/类别不能单独证明有草坪、座位等体验条件；独立模型还要对照完整原话审查。
- 单张卡引用错误只拒绝该卡，不拖垮整个后续批次。已出现卡片位置保留。
- 审查核对实体范围和资料时效；核实用reference_date与用户未提供的出游日期严格分开。
- 新推荐对象已能通过原业务执行器收藏：按当前会话绑定服务端真实地点，忽略客户端伪造名称。
  新`PlaceIdentity`仅含真实地点元数据，不伪造旧版匹配分、热度排名或六类标签。
  沿用登录、CSRF、幂等与跨账户保护。**前端统一聊天和新计划/历史快照仍未接入。**

下表的真实运行发生在本阶段最终章节索引/资料时效修正之前。保留原报告，不据此宣布最终准确率通过。

后续一次现有真实模型反例审查（0次搜索）同时拒绝了：

1. 用“苏州园林”集合介绍证明拙政园内某一坐标点是独立去处。
2. 用2016游客评论证明2026仍能在茶室坐着看江。

这是两条反例的审查改善证据，不是最终版本的完整南京流程重跑，也不是总体准确率统计。
最终又修复索引章节归属、读取不续期、预算边界和错误引用发布；后续完整真实验收仍需继续。

## 取舍与研究依据

借鉴[Adaptive-RAG](https://arxiv.org/abs/2403.14403)按需求复杂度选择检索量的思想，
以及[Self-RAG](https://arxiv.org/abs/2310.11511)对检索必要性和证据支持的区分。
本实现没有声称复现这些论文训练方法，也没有更换模型或加入新的框架。
[Tavily官方实践](https://docs.tavily.com/documentation/best-practices/best-practices-search)
支持查询相关片段、有限并发、URL去重与实际usage统计。

仍需解决：全站对话路由、新结果比较/计划/历史串联、集合/别名实体判断、来源可信性与时效、
独立新表达的需求匹配、多体验排序，以及真实设备/SDK/并发与P95。当前持续目标保持进行中。
