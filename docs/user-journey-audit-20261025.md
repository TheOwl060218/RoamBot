## 确认的问题

### P1：地图里的加入提示可见，按钮却不可交互

复现：地图选景点→加入行程成功→上方显示“已加入 / 更换行程 / 查看”。DOM检测 toast 的祖先为 inert；真实坐标点击“更换行程”后仍只有地图，没有出现行程选择器。保存本身已成功（随后行程中心可读），故属于弹层交互失效，不是新增地点后端失败。

原因：ItineraryProvider 的通知留在应用根节点内，LocationMapDialog 通过 Portal 成为活动模态层后，useModalLayer 将根节点设为 inert。提高 z-index 只能让通知可见，无法解除交互屏蔽。手机端通知换行后也会覆盖地图上部。

修复方向：通知应进入当前活动层，或由统一层管理支持可交互附属层；保留必要的背景 inert 和焦点隔离，不通过删除全部模态保护解决。

证据：`map-toast-inert.png`、`mobile-map-added-toast.png`；位于 test-results/journey-20261025。

### P2：地图两个入口的返回行为不一致

新增“地图”入口选点后关闭，可正确回位；另一条路径“湖滨公园详情→查看位置→地图选涌金公园→关闭地图”仍回到湖滨公园详情。选中的涌金卡片没有成为返回内容，用户容易误以为没有选中。

原因：详情的 detailId 和地图的 mapFocusId 分开保存，closeMap 只弹回原详情历史。上一批为了保留旧返回层级没有联动这个入口。本次从完整用户体验角度记录为一致性问题。

修复方向：统一返回目标跟随选中景点，并保持 Back/Forward 层级有效，不只对新地图入口生效。

证据：`detail-map-returns-old-place-final.png`。初次截图碰到正常320ms退出动画，另存稳定帧，不把瞬态残影算作持续遮挡。

### P2：恢复推荐后，原输入标题被改写

实际“明天想在杭州找几个适合散步、能看看湖景的公园。”返回推荐后显示为“杭州适合散步且能看湖景的公园有哪些？”，南京同样变成改写问句。聊天原文、日期和历史记录没有丢失。

定位：restoreDiscoveryResult 的结果标题优先 snapshot.search_request，再考虑 saved.message；模型改写覆盖原输入。历史详情使用 history.request.message，所以与主推荐页又不一致。属于展示/恢复规则问题，不能说成聊天存档失败。

### P2优化项：天气取数较密集

两轮仅最终展示8/7地点，但对应运行时间窗记录33次天气Provider请求。事实阶段在最终选择前对候选逐点取天气，同城近距离预报存在复用空间。数据均正常返回，尚不是天气故障；应区分请求日志与实际账单，未核对供应商账单金额。可参考现有行程模块的区域代表点预报复用，后续再评估质量和成本。

低优先级：莫愁湖开放时间有重复日期/多时段原文；收藏列表把已知“公园广场·公园”泛化为“地点”，详情里类型仍正确。均不阻止保存。

## 不计为业务故障的情况

- 在两个同源页面/iframe间使用同一测试账号，auth/me轮换CSRF后，含收尾退出操作的最终日志有7次写请求403。其后客户端刷新令牌、重发成功，未显示最终业务失败或重复对象。没有把403隐藏成所有请求一次成功；没有因为这些拒绝重新发起推荐。
- 测试工具 fill 日期仅改变DOM值，没有触发该浏览器日期输入的React状态；改用原生键盘日期选择后，表单状态与日期保存一致。初次日期未变不计后端失败。
- iframe高度844大于验收工具截图视口，工具点击滚出外层视口的关闭按钮有一次“找不到位置”；Escape能正常关闭，非已证明的产品按钮故障。窄屏证据属于桌面浏览器iframe，不是手机实机。
- 主推荐和历史页卡片底部在滚动容器外时会被裁切，实际滚动后比较/加入/地图入口可到达；没有复现之前聊天区大面积直接压住按钮的故障。地图加入通知是独立确认的覆盖/不可点问题。
