## 真实模型发现的改动

现有 `qwen3.7-plus` 在单轮多个 native tool calls 中实际多次只返回第一步。按 Qwen 官方说明启用多工具参数后仍复现，故改为一次原生函数调用返回最多六项有序、逐项类型化业务步骤，执行器顺序绑定新对象。

另发现模型可能使用从 0 开始的序号，或把生成邀请顺带扩展为复制链接；合同增加序号下界和明确说明，剪贴板工具仅在明确复制请求时开放。真实失败不改写为通过，原句复验结果记在验收文档。

### 2026-10-22 游客登录后保留推荐并接续收藏；去除横滑栏矩形阴影

用户复现：游客自然查询后说“收藏第一个”，登录完成却丢失原列表。定位为双端共同原因：DiscoveryPage与CommandRoot把游客→登录也当换账号清空；DiscoveryJobs按guest/user+session分隔，前端强行保留也会404；业务理解job又在401后删除，不能复用原动作。

实现：仅成功登录/注册后，以请求真实HttpOnly游客身份和新SessionGrant生成的账号会话scope，在DiscoveryJobs锁内转移该游客仍有效的job归属，不接收客户端user_id/job_id完成移交；删除旧游客cookie，旧guest、另一浏览器/另一用户/同账号其他新会话均不能接管。运行任务保留冻结计算scope，不因改变缓存执行身份使旧批次失效；所有后续HTTP权限仍由新registry归属检查。

前端只对guest→user保留当前推荐对象、选中/详情与聊天，退出或换账号仍清空。登录后当前完成推荐通过既有CSRF接口保存私有历史，原列表DOM与地点ID不替换。保存历史期间标记page_loading，使命令等待归档上下文稳定，避免新增history_id导致fingerprint误判页面改变。

只在尚未取得执行方案的401时保存待登录意图，保留服务端原intake；成功登录且当前页面/结果版本/焦点/选择/层级仍匹配才用新账号、新request_id重新提案，复用原intake避免再调用模型，不复用游客签名方案或未知写入。普通业务执行照原权限/确认/幂等约束。取消登录立即清理待续命令与intake；登录成功不重复添加用户输入消息。业务intake清理由CommandRoot统一接管，避免原页面finally在401时提前删除。重新检索、切页或改选后不会偷偷在新对象上执行旧意图。
