# 通用推荐机制：本轮变更与失败证据

目标仍是稳定地把自然需求转成合意结果。本轮没有完成正式可用验收，
也没有为酒店、博物馆或某一句话增加生产特殊规则。

## 已修改

- 体验合同区分`required`与`preferred`，保留逐字原文引用。
  默认流程和协调器共用条件/证据校验；硬条件必须有支持，偏好未证实不直接淘汰。
  已声称满足的偏好仍检查真实地点绑定与网页片段，重复/未知条件编号不能绕过校验。
- 提名和理由生成的`goal`改用用户本轮原话，完整多轮对话与当前上下文照常提供。
  模型摘要保留作诊断，不再作为下游需求权威，避免摘要把偏好升级为要求。
- `user_request`与`retrieval_hypotheses`分开提供；明确活动的独立审查不接收额外检索假设。
- 提名输入不再直接截取资料前18条。全体资料先按词元相关性、新信息和重复度选择，
  保留新付费检索资料的评估机会。地图候选窗口兼顾实际Provider类型差异，完全不读评分。
  这是模型输入窗口选择，不代表已经实现最终语义排序或满足多样性。
- 提名、理由整理和独立审查可返回`EvidenceNeed(place_id, query)`。
  只接受当前真实候选ID、去重，补查优先针对具体地点；缺口不写入用户条件或公共偏好。
  协调器工作线程不修改运行状态，缺口经身份、版本和取消检查后统一提交。
- 检索计划缓存升级v14，提名v5，协调器组合/审查缓存签名升级，避免旧合同混用。

未引入类别黑名单、固定类别配额、新模型、新框架或新的搜索服务。
原有权限、真实实体、路线硬上限、原文引用和网页事实检查继续保留。

## 下一步必须处理的通用缺口

1. 补查要关联具体必要条件，避免把可取舍偏好的未知情况消耗成首要阻塞任务。
   目前`EvidenceNeed`有真实地点绑定，但尚无条件编号及必要性绑定。
2. 当前每卡必有网页片段，是现有实现选择，并非用户要求。
   应改为按具体事实选择可信来源：地图登记事实可用地图证明；
   设施、服务、当前活动等需要对应依据，名称或宽泛分类不能自动证明具体可参与性。
   放宽“每卡固定来源数量”不等于放宽事实真实性。
3. 检索先保证核心活动的召回，再按偏好比较；仅靠提示没有程序上的语义保证。
   不得将本例预约词写入词表，应用通用需求合同和查询/缺口关联机制。
4. 实测提名合计约29.5秒，占本轮主要等待；应减少已核实实体的重复提名和冗长输出。
   单次耗时不能代替稳定延迟统计。
5. 输入窗口去重不等于最终推荐多样性。仍须在符合核心需求的真实候选上核验召回、
   语义筛选、类内排序、穿插及追加位置稳定，保留酒店偏科的既有未通过结论。

持续目标未完成，正式可用性未通过。
