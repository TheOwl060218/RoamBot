## 一、仍待统一调整

### 1. 页面整体排版

- 重新平衡桌面端左右两栏。当前左侧筛选区域较早结束或停留在上方，右侧结果卡持续向下延伸，视觉重量明显失衡。
- 降低单张推荐卡的纵向占用和重复信息密度，使多个结果更容易连续比较；不只缩小某个局部栏目，而是统一调整结果区的信息结构。
- 保持手机端上下排列和完整可操作性，不能为了桌面端紧凑而造成移动端文字挤压、溢出或控件重叠。
- 表单某一字段出现行内错误时，不得拉伸同一行其他输入框或改变原有输入框高度；开始日期与结束日期等成对字段需要保持顶部、输入框和错误区域稳定对齐。
- 为行内错误保留稳定的消息区域或采用顶部对齐布局，避免错误出现和消失时造成整行跳动。

### 2. 全站视觉规则

- 当前只确定“全站统一”的原则，不预先锁定具体色值、边框粗细、圆角、阴影或卡片样式；这些细节在功能问题完成后通过专门的前端讨论和页面对比再决定。
- 最终前端统一使用一套主题变量管理主色、辅助色、文字色、背景色、边框色、状态色、圆角、阴影和焦点样式，避免不同页面和弹窗各自形成一套视觉语言。
- 推荐、收藏、历史、账户、登录弹窗、历史详情和分享界面的按钮、输入框、卡片、提示条、空状态与加载状态使用一致的颜色语义和边框形式。
- 主色保持克制、和谐，成功、提醒、危险和信息状态使用独立但协调的辅助色；不能只依靠红绿区分含义。
- 相同层级的面板使用相同边框、圆角和间距规则；不通过无意义的卡片嵌套或过多装饰制造层级。
- 所有交互状态统一覆盖默认、悬停、键盘焦点、按下、禁用、加载、成功和失败，且状态变化不能造成控件尺寸跳动。

### 3. 出游匹配指数与状态颜色

- 统一设计“适合前往、谨慎安排、不建议前往”等状态与指数的颜色语义。
- 不预设红色一定代表推荐、绿色一定代表正面；颜色只作为辅助，必须始终保留明确的文字状态。
- 天气不佳的地点可以继续出现在列表中，但需要让状态与普通推荐有明显区别，并明确说明不建议前往的日期或时段。
- “出游匹配指数”只用于比较本次候选地点，不得通过颜色或文案包装成官方评分。

### 4. 结果卡信息结构

- 单人模式只展示主出发地距离，不能出现“同行”“平均路程”或多人差异信息。
- 多人模式继续展示每个出发地到地点的距离和用时；原“同行均衡”改为四字标题“出行差异”，使用“差异很小/差异较小/差异较大/差异很大”四档。
- 在结果区统一说明一次：正常路程和预计用时按查询时驾车路况估算，仅供参考；标有“直线估算”的结果仅按直线距离参考。
- 面向用户的标题继续使用“推荐理由”，不改成“推荐分析”。
- 推荐理由保持自然、可读，避免在卡片中重复已经清楚展示的字段，也不能出现无数据依据的“湖景优美”“必去”等描述。

### 5. 查询过程反馈

- 用户提交推荐或指定地点评估后，需要立即显示清晰的计算中状态，并暂时禁用重复提交。
- 第一版使用不显示数字百分比的视觉进度：提交后从起点平滑推进，请求未完成时逐渐放慢并停留在约 85%-90%，同时保持轻微活动状态。
- 配合“正在综合地点、路程、天气与推荐理由”等简短文字，明确中间长度只是加载反馈，不代表后端真实完成比例。
- 推荐接口成功返回时，由同一个前端完成事件把进度条推进到 100% 并展示结果；进度条只在真实成功后到达 100%。接口失败时不得显示 100%，应停止加载并展示对应错误。
- 只有后端未来提供真实的阶段事件时，才升级为“地点检索、路程计算、天气查询、推荐理由生成”等真实分阶段进度。
- 上述反馈规则要扩展到全站异步操作。耗时较长的页面级请求使用统一进度反馈，收藏、分享、删除、登录和历史重新查询等按钮级操作使用统一的加载图标、处理中标签和禁用状态。
- 历史“重新查询”第一次点击后必须立即取得前端请求锁并显示“重新查询中…”，完成前忽略后续点击；不能只依赖下一次 React 渲染后才禁用按钮。
- 一次历史重新查询最多创建一条新记录。成功后只导航一次；失败时释放请求锁、保留原历史并显示统一错误提示。

### 6. 历史删除与分享交互

- 删除单条历史、清空历史和撤销分享不得继续使用浏览器原生 `window.confirm`。改用全站复用的确认对话框，包含明确标题、影响说明、取消按钮和带动作名称的危险操作按钮。
- 自定义确认对话框需要与账户弹窗共享键盘焦点、Esc 关闭、背景遮罩和可访问性规则；具体颜色、边框、圆角和阴影留到统一前端设计阶段决定。
- 分享创建成功后，操作区不能突然变成两个只有图标且含义不清的按钮。复制链接和撤销分享应使用图标加文字或提供同等清晰的可见标签。
- 创建、复制、撤销和失败状态需要在稳定位置反馈，不能挤到操作按钮下一行导致卡片布局变化；“已复制”可以使用统一的短暂状态提示。
- 分享操作必须沿用全站异步按钮规则：第一次点击后立即锁定、显示处理中状态，完成前忽略重复点击；撤销分享属于破坏性操作，需要使用统一确认对话框。
- 历史卡片上的查看、重新查询、分享和删除需要重新组织主次关系，避免一排等权按钮造成视觉拥挤；具体排版在后续前端设计阶段统一讨论。

### 7. 推荐页面状态保留

- 用户从推荐页面进入收藏、历史、历史详情或账户界面，再返回推荐页面时，恢复离开前的完整表单草稿和最近一次查询结果，避免误触后重新填写或重复调用 API。
- 草稿包括模式、城市、日期、主出发地、同行人、最大距离、风景类型、匹配方式、目标地点和当前权重；推荐模式与指定地点评估各自保留状态。
- 推荐模式和指定地点评估共同使用的城市、日期、出发地、同行人、最大距离与权重在模式切换时直接保留；模式独有的风景类型、匹配方式和目标地点分别保存，不能因认证表单需要清空而误用通用表单重置逻辑。
- 第一版只在当前浏览器标签页的应用内存中保存，关闭标签页、退出登录或明确重置时清除；不把详细出发地址长期写入 `localStorage`。
- 返回推荐页面时不自动重新查询，保留原结果的生成时间和来源状态，让用户自行决定是否再次提交。

### 8. 地址输入提示

- 主出发地和同行人出发地接入高德输入提示服务。输入至少两个汉字或三个拉丁字符，并停止输入约 450 毫秒后才请求；每次最多显示五条候选，取消过时请求并短期缓存相同关键词，避免每次按键都消耗 API。
- 出发地候选使用目的地城市作为优先排序提示但设置为非严格城市限制，必须允许苏州出发去上海等跨城场景；用户在关键词中明确输入其他城市或校区时，可以返回对应外地地点。
- 指定地点评估的目标地点候选可以优先限制在用户填写的目的地城市内；推荐地点模式的最终候选地点仍由目的地城市约束，不能把出发地城市与推荐城市混为一谈。
- 候选项展示地点名称、所属区域和简短地址。用户选中后同时保留高德 POI ID 与坐标，后续请求优先复用坐标，避免再次地理编码；用户继续编辑文本时立即清除原选择的隐藏坐标。
- 用户不选择候选项时仍可提交自由文本，维持当前流程；输入提示服务失败时只隐藏候选并允许继续输入，不能阻断推荐或指定地点评估。
- 最近使用过的出发地可以在输入框聚焦时作为本地零调用候选，但不得长期明文保存详细地址到不受控的浏览器存储中。

### 9. 收藏反馈与收藏页面

- 收藏成功或取消收藏后，在页面上方显示不推动布局的短暂半透明提示，例如“已收藏：金鸡湖”或“已取消收藏”；失败提示需要清晰说明操作未完成。该提示与复制分享链接等全站短暂反馈复用同一组件。
- 推荐卡的收藏图标由爱心改为同尺寸星形。未收藏时为空心星，收藏成功后变为实心黄色星；异步请求期间立即锁定按钮，失败时恢复原状态并提示，不能因图标切换改变按钮尺寸。
- 收藏列表不再只展示不可进入的静态栏目。收藏卡主体可进入“评估指定地点”模式，自动填入收藏地点并保留当前标签页中已有的日期、出发地和权重，但不得自动发起 API 请求。
- 收藏卡中的删除操作保持独立，点击删除不得触发卡片跳转；原“重新评估”按钮与卡片主入口功能重复时应合并，避免重复操作入口。
- 高德原始分类字符串不得直接展示给用户，例如“地名地址信息;自然地名;湖泊”应映射为“湖景”等已有用户标签；无法可靠映射时宁可省略原始分类。

### 10. 账户操作反馈与敏感表单清理

- 注册并登录、普通登录和退出登录成功后，使用全站统一的顶部短暂提示明确反馈“账户创建成功”“登录成功”或“已退出登录”；失败继续在弹窗内显示可执行的错误信息。
- 登录弹窗关闭后不得保留密码。成功登录、成功注册、退出登录、点击关闭或按 Esc 关闭时，都需要清空密码、用户名、错误信息和“显示密码”状态，重新打开时显示干净表单。
- 当前弹窗虽然在 `open=false` 时不渲染，但组件仍然挂载，内部 `username` 与 `password` 状态不会自动消失；修复必须显式重置状态，不能只依赖隐藏弹窗或浏览器刷新。
- 表单状态清理与浏览器密码管理器是两个层面。应用不得自行保存明文凭据；实现后仍需分别验证普通关闭重开和浏览器已保存密码时的行为，确保页面自身不会泄露上一次输入。
- 登录时不再因密码少于 8 位而单独显示密码长度要求。用户名不存在、密码错误或登录输入不符合密码长度时，统一显示“用户名或密码不正确”，避免通过文案确认某个用户名是否存在。
- 在统一登录失败提示旁增加小型问号帮助图标，说明“创建账户时，密码长度要求为 8–128 位”。帮助内容必须同时支持鼠标悬停、键盘聚焦和手机点击，不能只依赖桌面端悬停。
- 注册页面继续明确展示并校验密码长度为 8–128 位；暂不增加“必须同时包含英文字母和数字”等组成规则，避免与现有账户的创建规则不一致。

### 11. 每日天气卡

- 为“晴、多云、阴、雨”等天气状态增加图标，优先复用现有前端图标库；放大天气状态文字，使其成为卡片中的主要视觉信息之一。
- 温度范围必须带提示词，例如“温度 27–37°C”，不能直接在日期下方孤立显示“27–37°C”。
- 重新组织日期、天气状态、温度、出行建议和说明文字的层级，避免四行文字以近似字号和间距连续堆叠。
- 两日至七日天气卡使用稳定、规整的时间序列布局；五日数据不得出现不协调的 `4 + 1` 孤立换行。
- 日期继续使用“7月25日”格式，不退回“07/25”。
- 前端不得显示“极端温度 -40”等内部扣分值，只展示自然语言天气影响和可执行建议。
- 室内场馆应说明高温对馆内游览影响较小，同时提醒往返途中避开高温并注意防暑；户外地点应更明确地提示高温、紫外线、降雨等风险。

### 12. 数据来源与降级提示

- 地点评分继续显示为 `4.8 / 5` 一类原始值，不使用“评价优秀、评价良好”等主观等级词。
- 评分来源与指数用途在结果区统一说明一次，不在每张卡重复。
- 正式版本不为正常的新鲜缓存命中显示“缓存数据 / 使用未过期缓存结果”这类技术提示。
- 后端缓存功能保留，用于降低 API 成本和提高可用性；只有外部服务故障并使用旧数据时，才显示面向用户的数据时效提醒。
- 正式发布前清除开发和手工测试阶段形成的缓存记录，使用干净的数据卷。

## 二、已经实现且必须保留的约定

- 推荐权重使用一根三段比例条和两个分界按钮，显示天气、距离和地点评分三个比例；不恢复为三根相互联动的滑杆。
- 多人公平性不作为第四段暴露给用户；三项可见比例共同占 80%，后台固定加入 20% 的多人差异因素。
- 推荐卡总值继续称为“出游匹配指数”，不改回“总分”或“推荐分数”。
- 地点评分数据来源为高德开放平台；没有评分时显示“暂无数据”，不能把缺失评分当成低分。
- 每日卡和推荐卡不展示内部天气分、距离分、扣分明细等实现数据。
- 指定地点评估只返回目标地点，不要求选择风景类型；推荐模式与指定地点评估继续使用清晰的模式切换。
- 推荐数量不是必须凑满五个，可以少于五个，最多七个；不能为了凑数返回不相关地点。

## 三、现有内容完成后的增强项

- 可以让地点名称、标签或结果卡进入地点详情视图，展示已有的地址、评分来源、天气和各出发地信息。
- 推荐卡可以使用高德 POI 返回的地点照片增强辨识度，但图片必须直接融入卡片而非嵌套成带边框的小图片框。已确认的视觉方向为“左侧画面较强、向右逐渐减弱并保护右侧指数可读性”；图片具体放置位置、卡片高度和文字层级需要在整张推荐卡重新排版时统一决定，不能沿用当前试验稿直接实现。
- 地点照片属于可选增强：只有来源明确、内容与地点匹配、清晰度和构图适合当前容器时才展示；照片缺失、失效或不适配时必须自然回退为完整的纯文字卡片，不能使用不相关图片或破坏版式。
- 推荐列表优先在现有高德搜索请求中一并请求照片字段，不为每张卡额外调用；收藏详情仅在用户主动点开某个地点时按 POI ID 查询并缓存，收藏列表加载时不得批量请求详情。
- 高德字段可用于展示图片标题、评分、营业时间和联系方式等事实信息；若需要自然语言介绍，只能根据已验证事实生成简短摘要，不得编造景色、荣誉、开放状态或游玩体验。
- 不同出行方式的预计时间只在用户打开某个地点并主动查询后调用，结果需要缓存；不得为所有候选地点预先批量请求。
- 该增强项不包含地图绘制、路线展示、导航或具体行程安排，避免重新突破已确认的项目边界。
- 账号可以默认使用用户名首字母头像，并允许用户从少量预设图标和颜色中选择；暂不支持上传图片或接入第三方账号头像。

## 2026-08-03 Live 实际测试新增问题

- 本节最初记录过一次“游客核心查询返回 `401 Unauthorized`”的旧现象；最终产品契约已改为游客可使用地点推荐和指定地点评估，仅收藏、历史、分享等个人数据操作要求登录。
- 若无效会话或个人数据操作返回 `401`，前端需明确提示登录并打开账户窗口；不得把认证失败误报为地点、天气或推荐服务故障。游客核心查询不写入个人历史。
- 移动端紧凑候选切换器使用首尾循环：第 1 项向左切换到最后一项，最后一项向右切换回第 1 项；候选地点不少于 2 个时，两侧按钮始终可用。
